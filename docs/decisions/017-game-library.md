# OPFS 游戏库与持久资源

游戏库把用户主动保存的资源保存在浏览器中。先从本地文件或远程链接载入游戏，再点击“保存当前游戏”；之后可从游戏库启动、修改名称/入口/执行后端，或移除资源。远程来源在保存时完整复制，资源服务器断开后也能读取尚未使用的成员。应用外壳的离线加载由后续落地的 [PWA 模块](018-offline-app.md) 提供。

## 模块与线程

- `app/game-library.ts` 管理页面操作、进度、错误、容量显示及启动设置。
- `player/library-client.ts` 与独立 `workers/library.worker.ts` 通信。复制与校验不会占用会话 VM 的执行队列。
- `player/library/service.ts` 负责身份、预算、发布事务、恢复和锁的生命周期；`records.ts` 定义并校验目录与文件清单。
- `backends/files/opfs-library.ts` 负责字节写入、分块校验和读取缓存；`library-index.ts` 负责 IndexedDB 事务。
- 游戏库接入时 Session 协议升级为 3，后续 [图形恢复](019-graphics-recovery.md) 将当前协议升级为 4。`GameInput` 可以是有序的 File/URL 集合，也可以是 `{ libraryId }`。Worker 在创建 VM 前取得库资源的读取租约，之后仍以 `SourceFile`/`ByteSource` 进入既有归档与资源层。

引擎和归档解析器不访问 IndexedDB、OPFS 或游戏目录。TJS 的游戏存档继续使用原有 `krkr2-web` 数据库；移除库资源不删除存档。游戏库与存档的数据生命周期因此可以独立管理。

## 写入与发布

导入持有站点级独占 Web Lock，创建随机 UUID 目录；源文件按原始选择顺序写入数字文件名。逻辑资源名、路径大小写、重复来源和远程版本另存在清单里，不转换为宿主文件路径，也不改变补丁覆盖顺序。

复制每次读取最多 1 MiB，支持超过单资源解码预算的源文件。每块计算 SHA-256，处理同步写入的短写，检查最终文件长度，调用 `flush()` 后关闭访问句柄。零长度文件同样创建并关闭。写入中途或 flush 失败不会提交游戏记录。同步访问句柄只在 Worker 使用，接口语义见 [File System Standard](https://fs.spec.whatwg.org/#api-filesystemsyncaccesshandle)。

全部文件关闭后，重新检查存储来源的游戏身份，然后在同一个 IndexedDB 事务中提交完整清单和小型目录摘要。只有事务完成才显示“已保存”。IndexedDB 与 OPFS 不构成共同的事务：发布前的文件属于临时数据，发布完成的记录才是可见游戏。

数据库 `krkr2-library` 当前版本为 2，包含 `games`（完整文件/校验清单）和 `catalog`（名称、入口、后端、体积等摘要）。二者增删改使用同一事务；读取列表只访问 catalog，启动时才读取目标游戏清单。版本 1 的完整记录会在升级事务中生成摘要，保留原有身份、资源和设置。升级失败保留旧数据库。

## 中断、恢复与删除

正常取消中断 HTTP 请求，在关闭当前文件句柄后移除未发布的 UUID 目录。取消 RPC 两秒内不能完成时，客户端终止导入 Worker；这是处理无响应浏览器操作的兜底路径。下次打开库或开始导入时，在独占写锁下删除没有已发布记录的受管 UUID 目录。恢复只扫描本应用的 `krkr2-library-v1` 命名空间，不删除未知命名的文件或其他站点数据。

若取消与最终提交竞争，以 IndexedDB 的事务结果决定是否发布；已经提交的完整游戏不会作为临时数据清理。清理暂时失败时可能留下占用空间的孤立目录，后续恢复再处理，不伪造成功的游戏记录。

会话从准备阶段开始持有该库条目的共享 Web Lock，暂停时继续持有，停止/失败取消和 Worker 退出时释放。删除需要对应的独占锁，其他标签页正在运行时会明确拒绝；共享/独占锁语义见 [Web Locks](https://w3c.github.io/web-locks/#lock-mode)。当前页移除正在运行的库条目，会先停止当前会话。

删除先提交目录记录移除，再清理对应的资源目录。若后者失败，记录不会重新出现，后续恢复负责清除残留字节。界面的站点存储用量来自浏览器估计，不把目录中的逻辑体积误当成实际磁盘占用。其他标签页通过 BroadcastChannel 或窗口重新获得焦点时刷新列表；正在编辑的设置草稿保留。

## 来源身份与读取校验

本地来源保留此前的路径/大小/首尾采样身份，库中启动与临时导入共享同一存档命名空间。远程保存会重新打开来源，并比较当前游戏的固定身份；URL、重定向目标或版本变化时，要求重新载入，避免将新版本内容保存到旧版本的进度下。

存入 OPFS 的远程文件保留原有远程身份，库中运行不依赖原 URL，也不向该服务器重新验证。之后即使服务器删除资源，库中的副本仍可读；重新导入更新版本则是另一份记录。相同游戏可保存为多个库条目，条目 UUID 和存档 game ID 是两个概念；不会仅按 game ID 去重而丢失不同的覆盖顺序。

所有库文件按需读取完整的 1 MiB 校验块。块的 SHA-256 必须与清单一致，EOF 块按实际长度处理；文件截断会在打开时发现，内容损坏在首次触及对应块时发现。缓存与返回给调用方的数组相互独立。任何块校验失败都使当前库来源池失效，先前缓存也不能继续冒充有效内容；存档覆盖层仍然独立。

这不是抗同源脚本篡改的认证机制：有权修改同一站点数据的代码也能修改清单。它用于识别存储损坏和意外变更，不替代发布包签名。

## 容量与平台边界

| 项目 | 限制 |
| --- | --- |
| 游戏库目录 | 最多 256 个条目 |
| 单条目来源 | 最多 10,000 个，逻辑路径最多 1,024 字符 |
| 单条目资源 | 最多 64 GiB，且全部文件合计最多 65,536 个校验块 |
| 单条目清单 | 编码后最多 8 MiB |
| 顺序复制 | 每次最多 1 MiB，逐文件 flush/close |
| 会话读取缓存 | 32 MiB LRU，文件间共享，最多 64 个在途校验块 |
| 单次资源读取 / 在途输出预留 | 64 MiB / 会话合计 128 MiB |

这些是组件保留和在途预算；Web Crypto、OPFS/Fetch 内部缓冲、清单序列化及后续归档/媒体解码还有瞬时内存。来源可以大于 4 GiB，但单个展开资源与媒体的既有解码预算仍然适用。

导入前读取 `navigator.storage.estimate()` 并检查预估剩余容量；浏览器实际写入或事务抛出的配额错误仍是最终依据。界面提供由用户点击的 `persist()` 请求，显示是否被授予持久存储；未被授予也可继续使用游戏库。授权并不防止用户清除站点数据，存档仍应可导出备份。规则见 [Storage Standard](https://storage.spec.whatwg.org/#persistence)。

API 存在不等于存储可用。当前 Playwright WebKit 的临时上下文调用 `getDirectory()` 会返回 UnknownError，而使用独立磁盘 profile 可以正常工作；没有将错误文案中的 “out of memory” 当作内存不足的证据。游戏库测试为三种浏览器分别创建并清理隔离的磁盘 profile，另外用默认上下文验证拒绝存储时临时载入和存档继续可用。没有声称所有 Safari/隐私模式都可写 OPFS。

## 验证与后续

`tests/conformance/opfs.test.ts` 验证清单/路径、短写、flush/配额/取消失败、超过 64 MiB 的分块复制、超过 4 GiB 的读取、LRU/并发/独立副本、校验损坏和停止后防止缓存复活。

`tests/library-browser/library.spec.ts` 使用真实 OPFS、IndexedDB、Web Locks 与 TJS WASM。覆盖本地及远程 XP3/ZIP、断开资源服务器后的新资源访问、刷新和浏览器进程重启、存档身份、设置、删除占用、配额/写入/flush/提交故障、Worker 强制终止后的孤立文件恢复、取消网络复制、版本变化、延迟发现的块损坏，以及目录升级。另检查窄屏布局与文本安全显示。

测试注入使用带唯一查询参数的 Worker URL，避免 WebKit 将上一轮人为注入的故障脚本作为同 URL 资源复用。生产 Worker 仍使用 Vite 的内容哈希 URL。此前的原生核心、媒体、输入、归档与图形测试继续纳入完整回归。

尚未实现按块的持久 HTTP 缓存、下载续传、库条目之间的资源去重、自动驱逐或完整游戏包导出/身份迁移。当前保存会完整复制所选来源，存档可使用既有导出功能；这些剩余项继续保留在非插件目标内。PWA 应用外壳缓存的设计和证据另见离线应用决策。

持久化测试由 `playwright.library.config.ts` 单独配置，使用浏览器启动时已创建的页面；常规临时上下文回归使用原配置。`npm run check` 和 `npm run test:browser` 顺序执行常规、游戏库和后续加入的 PWA 三套浏览器配置，各保持 2 个 worker、30 秒用例上限和 12 秒断言上限。仅运行库测试可用 `npm run test:library`。该拆分避免常规共享浏览器和额外的磁盘浏览器实例在同一测试阶段混用；没有跳过游戏库案例或放宽断言。

窗口重新获得焦点时，若目录未变化则保留原有节点，避免刷新恰好发生在鼠标按下与抬起之间时丢失启动点击。新增测试在这两个事件之间触发真实目录刷新，随后验证游戏启动和原存档恢复；窄屏测试也覆盖超长名称换行、文本显示及未提交设置草稿。

PWA 阶段回归发现本机 WebKit 的 trace 连续截图会显著增加磁盘双页面场景的协议延迟。对照后仅为 WebKit 关闭连续截图，保留失败截图、DOM/网络/源码 trace 和全部原有断言、并发及超时；证据见 [离线应用决策](018-offline-app.md)。
